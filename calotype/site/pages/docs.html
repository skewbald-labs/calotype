Basics

The API lives at https://calotype.dev. A successful screenshot returns the image itself. Everything else returns JSON. Errors always have the same shape:

{"error": {"code": "quota_exceeded", "message": "...", ...}}

The code is stable and meant for programs; the message is meant for people. Some errors add fields, listed under Errors. Every response carries an X-Request-Id header; quote it when you write to support.

Authentication

Every call except key creation, /v1/plans, /health and Stripe's webhook needs an API key. Send it in one of two ways:

  • a header: Authorization: Bearer cal_... (preferred);
  • a query parameter: ?access_key=cal_....

Prefer the header. A key in the query string is part of the request address, which travels through more systems than a header does. Calotype drops the hosting platform's request records before they are stored (see Privacy), but the header is still the safer habit. Calotype's own logs never contain the key. An Authorization header that is not a bearer token is refused, even if access_key is also set. The MCP endpoint takes the header only.

The key is the account. Calotype stores only its SHA-256 hash, so a lost key cannot be shown again.

Create a key

POST /v1/keys makes a free-plan key. It needs no body and no authentication, and asks for nothing about you. The button on the home page calls it.

curl -X POST https://calotype.dev/v1/keys

It answers 201:

{
  "key": "cal_...",
  "plan": "free",
  "monthly_quota": 100,
  "message": "This is the only time the key is shown. Calotype stores only its hash and cannot recover it."
}

Key creation is rate limited; see Quotas and rate limits.

Quota emails (optional)

A key can hold one email address. Calotype then emails it when the key reaches 80% of its monthly quota and again at 100%: at most two emails per key per calendar month, and at most four per address per month across all keys. Nothing else is sent to it. The address is never shown back in full; /v1/usage shows a masked form. See Privacy.

Give it when you make the key, as a JSON body:

curl -X POST https://calotype.dev/v1/keys \
  -H "Content-Type: application/json" -d '{"email": "you@example.com"}'

The answer adds "email": "y***@example.com" and "notices": true. A malformed address answers 400 invalid_email and makes no key. The check is light: one @, a dot in the domain, at most 254 characters. The domain is stored in lower case.

POST /v1/keys/email

Sets or replaces the address of the key that calls it. Body {"email": "you@example.com"}. Answers {"email": "y***@example.com", "notices": true}.

DELETE /v1/keys/email

Removes the address. Answers {"email": null, "notices": false}, also when there was none.

The link in each email

Every quota email ends with a link to /v1/keys/email/remove?token=.... Opening it removes the address at once; no key is needed. The link works only while the key holds the address it was sent to. Replying "stop" to the email works too. Revoking or deleting a key removes its address.

A server without quota emails set up does not store an address: POST /v1/keys still makes the key and answers "notices": false, and POST /v1/keys/email answers 503 notices_unavailable.

Take a screenshot

GET /v1/screenshot with the parameters in the query string:

curl -H "Authorization: Bearer $CALOTYPE_KEY" \
  "https://calotype.dev/v1/screenshot?url=https://example.com&width=1280&height=800" \
  -o example.png

Or POST /v1/screenshot with a JSON object as the body:

curl -X POST "https://calotype.dev/v1/screenshot" \
  -H "Authorization: Bearer $CALOTYPE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com", "full_page": true, "format": "webp"}' \
  -o example.webp

POST keeps the target address out of the request line. With POST, send the key in the header (or as ?access_key=); an access_key field in the JSON body is ignored.

Parameters

The same names work in the query string and in the JSON body. A parameter Calotype does not know is refused with invalid_parameters, so typos do not pass silently. In the query string, write booleans as true or false.

NameDefaultWhat it does
urlrequiredThe page to capture. http or https only, on a public address, at most 2,048 characters. Ports 80, 443 and 1024 and up. No user:password@ in the address.
width1280Viewport width in CSS pixels, 100 to 3840.
height800Viewport height in CSS pixels, 100 to 2160.
full_pagefalseCapture the whole scrolling page instead of the viewport. See the height cap below.
formatpngpng, jpeg or webp. jpg is accepted as jpeg.
quality801 to 100, for jpeg and webp only. Sending it with png is an error.
device_scale_factor11 to 3, decimals allowed. Use 2 for sharp images on high-density screens.
delay_ms0Extra wait after the page loads, 0 to 10,000 ms.
wait_untilloadWhen the page counts as loaded: load, domcontentloaded, networkidle or commit.
block_adsfalseBlock requests to a list of common ad and tracking domains.
dark_modefalseAsk the page for its dark colour scheme (prefers-color-scheme: dark).

Size limits

  • width × height × device_scale_factor² may be at most 80,000,000 pixels.
  • A full-page capture is at most 20,000 CSS pixels tall, and less where the 80,000,000-pixel limit bites first (wide viewports, high scale factors). WebP images cannot be taller than 16,383 pixels, so for webp the cap is 16,383 divided by the scale factor. A page taller than the cap is cut off at the cap; that is not an error.

The response

A successful call answers 200 with the image as the body and its type in Content-Type (image/png, image/jpeg or image/webp). Headers:

HeaderMeaning
X-Calotype-UsageScreenshots this key has used this month, and its limit, for example 12/100.
X-Calotype-Duration-MsHow long the capture took.
X-Calotype-Target-StatusThe HTTP status the page answered with. A page that answers 404 or 500 is still captured, and still counts; check this header if that matters to you.
X-Calotype-Truncated1 when the page passed the 50 MB download limit and the image shows what had loaded by then.
X-Request-IdOn every response. Quote it to support.

Images are sent with Cache-Control: no-store. Calotype keeps no copy: the image exists only in the response.

What Calotype will not fetch

Calotype only captures public web pages. It refuses private, loopback, link-local, carrier-grade NAT, multicast, reserved and cloud-metadata addresses, and host names such as localhost or names ending in .internal or .local. A host name must resolve to public addresses only; if any address it resolves to is private, the request is refused.

The check covers more than the first address. Every request the page makes goes through the same rule: redirects, images, scripts, frames, fetch calls and WebSockets. The browser's only route to the network is a proxy that resolves each host itself and connects to the exact address it checked, so a DNS answer cannot change in between. Non-web schemes such as file:, ftp: and chrome: are refused, as the address to capture and inside the page.

Each capture runs in a fresh browser context that is thrown away afterwards, with service workers and downloads off; nothing from one capture is visible to the next. Pages with an invalid HTTPS certificate fail to load. A page may download at most 50 MB in total. Each capture has 30 seconds from start to finish.

The reasons for each of these rules, and how to build the same defences for a browser you run yourself, are in A headless browser inside your network is an SSRF risk.

Please capture only pages you are allowed to view. The acceptable use policy has the rules.

Quotas and rate limits

  • Monthly quota. Each key may take as many successful screenshots a month as its plan allows: Free 100, Starter 5,000, Pro 25,000. Months are calendar months in UTC; counts reset at 00:00 UTC on the first day of each month. Unused screenshots do not carry over.
  • What counts. Only a capture that returns an image. Rejected requests (bad parameters, bad key, refused address, over quota) and failed captures (unreachable page, timeout, busy, internal error) are not counted.
  • Over the limit. Calls answer 429 quota_exceeded until the reset. There are no overage charges.
  • Key creation. At most 3 keys an hour from one IP address, and at most 200 an hour across the whole service. Over either limit, POST /v1/keys answers 429 rate_limited with Retry-After.
  • Free tries. The box on the home page takes a screenshot with no key: at most 5 tries an hour from one IP address, and at most 300 renders a day across the whole service, reset at 00:00 UTC. A try is always 1280 × 800, not full page, JPEG at quality 70 with ads blocked, under the same address rules and time limit as a call with a key. The API has no keyless calls.
  • Concurrency. Each server renders a few pages at a time. A request that waits more than 10 seconds for a free renderer answers 503 busy.
  • Time. 30 seconds per capture, from start to encoded image.

Usage, plans and health

GET /v1/usage

Your key's plan and this month's count. It needs the key and does not count as a screenshot.

{"plan": "free", "month": "2026-11", "used": 12, "limit": 100, "credits": 0, "resets_at": "2026-12-01T00:00:00Z", "key_ref": "3f9a0c71b2de", "email": "y***@example.com", "notices": true}

credits is the key's prepaid credit: screenshots paid for in advance, used only after the month's limit. It is 0 for every key until prepaid credit goes on sale.

key_ref names your key without giving it away: quote it when you write to support, and never send the key itself. email is the key's quota-email address, masked, or null; notices says whether quota emails will be sent.

GET /v1/plans

The plans, their monthly quotas and prices in US dollars. No key needed. provisional is true only on a server where paid plans are not on sale.

{"provisional": false, "plans": [{"name": "free", "title": "Free", "monthly_quota": 100, "price_usd": 0.0}, ...]}

GET /health

Answers 200 with {"status": "ok", "version": "...", "browser": true}, or 503 with "status": "degraded" when the renderer's browser is down.

MCP server

Calotype is also a remote MCP server, so an AI agent or coding assistant can look at a web page itself. There is nothing to install: point your MCP client at the address below and send your key in a header.

  • Address: https://calotype.dev/mcp
  • Transport: streamable HTTP
  • Header: Authorization: Bearer cal_...

In Claude Code:

claude mcp add --transport http calotype https://calotype.dev/mcp \
  --header "Authorization: Bearer cal_..."

In a client configured with JSON, such as a project's .mcp.json:

{
  "mcpServers": {
    "calotype": {
      "type": "http",
      "url": "https://calotype.dev/mcp",
      "headers": {"Authorization": "Bearer cal_..."}
    }
  }
}

Other clients that take a server URL and custom headers need the same three things: the address, the HTTP transport, and the Authorization header. Get a key with the button on the home page; it is free and asks for nothing.

The screenshot tool

One tool, screenshot, marked read-only. It takes url (required), full_page, width, height, format, dark_mode and block_ads, with the same meanings and limits as the API's parameters. Two defaults differ from the API's: format is jpeg and block_ads is true, which keeps images small for a model. It returns the image, and a line of text with the page's address after any redirects, the image's size, and the key's count for the month.

Each tool call goes through the same checks as /v1/screenshot: the same refusal of private addresses, the same quota, and the same rule that only a capture that returns an image counts. A refused address, a page that fails to load or a used-up quota comes back as a tool error that starts with the error code, such as quota_exceeded: ..., so the agent can read it.

Without a key, a client can still connect and list the tool, so directories and inspectors can see it; calling the tool then answers a tool error saying how to get a free key, and captures nothing. A wrong or revoked key answers HTTP 401 with a JSON-RPC error saying how to get a key. The key is read from the Authorization header only, never from the address. The endpoint is stateless and answers POST only; GET and DELETE answer 405. It speaks MCP protocol versions 2024-11-05 through 2025-11-25 over the initialize handshake, and 2026-07-28.

Billing endpoints

These endpoints let a key buy a paid plan, and manage it afterwards. The upgrade form on the pricing page uses them. A self-hosted copy without Stripe set up answers 503 billing_unavailable.

POST /v1/billing/checkout

With a free key and a body of {"plan": "starter"} or {"plan": "pro"}, answers {"url": "https://checkout.stripe.com/...", "plan": "starter"}. Send the buyer to that address. When Stripe confirms the payment, the same key moves to the new plan; nothing in your code changes. Stripe is given the key's internal number, never the key.

GET /v1/billing/portal

With a key that has paid before, answers {"url": "https://billing.stripe.com/..."}: a Stripe customer-portal page to change the card or plan, see invoices, or cancel.

POST /v1/billing/webhook

For Stripe only. It checks Stripe's signature and takes no API key.

Prepaid credit for agents (not yet live)

Not yet live. This endpoint is written and tested, but it is switched off on https://calotype.dev: it answers 503 billing_unavailable, and nothing can be bought through it today. The terms of service and the refund policy do not cover prepaid packs yet. This section describes how it will work, so that agent builders can plan for it. Until then, a key gets more screenshots through a paid plan.

It is for an agent that runs out of screenshots with nobody there to open a checkout page. The agent pays from its own wallet over the Machine Payments Protocol (MPP), and the screenshots are added to the key it already uses. Payment goes through Stripe, with a card held in a wallet that issues Stripe shared payment tokens, such as Link. Stablecoin payment is not built.

POST /v1/credits

Send the key and the pack to buy:

curl -i -X POST https://calotype.dev/v1/credits \
  -H "Authorization: Bearer cal_..." \
  -H "Content-Type: application/json" \
  -d '{"pack": "starter"}'

One pack is planned: starter, 5,000 screenshots for $19, paid once. It is not a subscription and is not charged again. GET /v1/plans lists the packs as credit_packs on a server where they are on sale.

  1. Unpaid, the answer is 402. The WWW-Authenticate header holds a Payment challenge with method="stripe" and intent="charge". Its request is base64url JSON with the amount in cents ("1900"), the currency ("usd") and the seller's Stripe profile. The challenge is valid for five minutes and only for the key that asked.
  2. Pay it. An MPP client does this step itself: it gets a shared payment token for that amount and builds the credential. With a card wallet, the wallet's owner may be asked to approve the spend.
  3. Send the same request again with the credential. The challenge says header="Payment-Authorization", so the credential goes in a Payment-Authorization: Payment ... header and the key stays in Authorization. A client that can only send the credential in Authorization puts the key in the address instead, as ?access_key=cal_..., on both requests.
  4. Paid, the answer is 200, with a Payment-Receipt header and the new balance:
{"pack": "starter", "screenshots_added": 5000, "credits": 5000, "already_credited": false,
 "payment": {"method": "stripe", "reference": "pi_...", "amount_usd": 19.0}}

Sending a paid credential again is safe: it charges nothing, adds nothing, and answers 200 with "already_credited": true. Keep payment.reference; it names the purchase if you ever write to support.

How credit is used

Each screenshot counts against the month's plan quota first. Only when that is used up does a screenshot take one credit, and the response then carries an X-Calotype-Credits header with the credit left. Credit does not reset at the start of a month and does not expire. A capture that fails takes nothing. GET /v1/usage shows the balance as credits.
